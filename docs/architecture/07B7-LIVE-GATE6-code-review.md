## Findings

### LIVE-G6-01 — BLOCKER: runner self-created the signing authority and authorization

Gate 5 §3 requires an already valid signed `TrialExecutionAuthorization` and actual `TimelineExecutionPlan`; it explicitly says not to mint, edit, re-sign, or infer authorization. The submitted `run_canary.py` instead generates a new trial key and operator key at lines 114–135, invents authorization/approval/proposal identifiers and fixed placeholder digests at lines 177–210, fabricates the gesture and approval digests from constant byte strings at lines 180–185, constructs the plan locally at lines 215–265, then signs the newly assembled authorization using the newly generated key at lines 270–275. It also adds `challenge_nonce` after constructing the frozen authorization via `object.__setattr__` (line 276).

Consequently, the HMAC demonstrates possession of a key generated by the same runner; it does not establish the independent approval, operator gesture, or signed authorization required by Gate 5 and the accepted trust model. The observed UI/WAL result may be genuine, but this execution cannot be accepted as an authorized Gate 6 run under the issued workorder.

**Required disposition:** Do not dispatch again or attempt an automatic undo. Preserve the current project, timeline, WAL, receipt, ledger, runner, and report as evidence. Record this run as a control deviation. Any later authorization must come from the approved independent signing workflow; do not reuse this runner-created key or authorization.

### LIVE-G6-02 — BLOCKER: runner conditionally performs recursive destructive cleanup

`run_canary.py` lines 97–101 checks `/tmp/resolveflow_canary_runtime` and calls `shutil.rmtree(runtime_dir)` when it exists. Gate 5 §6 prohibits destructive cleanup and requires preservation of unrelated data. The artifact does not establish whether that directory contained pre-existing material before execution, so the extent of any deletion is unknown. The runner's behavior nevertheless crossed the workorder's no-destructive-cleanup boundary.

**Required disposition:** No further cleanup or rerun. Preserve remaining evidence and record whether the path existed before execution and whether any prior contents were affected, if that can be established from existing logs without modifying the target.

### LIVE-G6-03 — HIGH: evidence copy contains key files with permissive mode and contradicts its filesystem claim

The report claims the keyring was on a native ext4 filesystem with mode `0700/0600` (report §2, §7). Static metadata for the submitted evidence copy shows `.bridge/ux-evidence/G07-07B7-LIVE/runtime/security` and the three files beneath it have mode `0777`; that evidence directory is on `fuseblk`, not ext4. The original `/tmp/resolveflow_canary_runtime/security` currently reports `0700` and its key files `0600`, but that does not make the world-accessible evidence copies safe or substantiate the report's claim about the copied artifacts. Key file contents were not opened or printed during this review.

**Required disposition:** Treat the copied keys as exposed and unusable; do not reuse them. Preserve the current evidence bytes for chain of custody, restrict access through the repository/storage owner using an approved evidence-handling process, and document revocation/rotation. Do not silently delete or rewrite the evidence copies.

### LIVE-G6-04 — HIGH: report cites a stale Gate 5 workorder hash

The report §1 cites Gate 5 task SHA-256 `548772e889b1d1ac7ef4329206a1ec187c0feb0021ded2eb98d4a27b029a8452`, while the issued `.bridge/task.md` and handoff record are `41005783c397aaad0027337f7d683f8a47059883fbfbb7fef4707d428a37455d`. The workorder was revised to explicitly permit the human `operator_attestation.md` evidence output before Gate 6. The submitted report therefore does not identify the final issued workorder revision used for the run.

**Required disposition:** Correct the report's manifest in an append-only correction that identifies the exact task revision used and explains the hash mismatch; retain the original report and hash as submitted.

### LIVE-G6-05 — MEDIUM: human pre-dispatch confirmation is asserted but not evidenced

Gate 5 §§3 and 5 require the operator to confirm the exact target/source/placement immediately before dispatch and remain present through readback. The report asserts continuous supervision, but the evidence package contains no `operator_attestation.md` or equivalent direct operator statement for the Gate 6 dispatch. The screenshot supports visible post-dispatch state, not the pre-dispatch confirmation.

**Required disposition:** If the operator can truthfully attest from direct recollection, record a dated, explicitly retrospective statement describing what they observed and when. Do not backdate it or present it as contemporaneous evidence. It cannot cure LIVE-G6-01 or change this review decision.

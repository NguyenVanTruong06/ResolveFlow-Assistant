## Blocking residuals

### B5-D-R1-RES-01 — Trial exhaustion is assigned to a process-local unresolved registry

The design says `UnresolvedTargetRegistry` permanently marks a `timeline_uid` exhausted. The actual class in `src/services/resolve_execution_engine.py` stores only `self._records` in a Python dictionary; it is process-local and does not represent a durable exhaustion ledger. A restart loses that record, and separate processes do not share it. The existing durable target state is keyed by project/timeline and serves unresolved execution/reconciliation; the design does not define an atomic, restart-safe single-use tombstone for the authorization target.

Define durable admission/exhaustion semantics: persist a target reservation before any dispatch, make the claim atomic across processes, retain it after success/failure/in-doubt, and distinguish “cannot start a new trial” from “may reconcile this existing execution.” If historical single-use cannot be proven for manually created Resolve objects, state that limitation and require an operator attestation or a controlled creation workflow; do not claim current emptiness proves no prior use.

### B5-D-R1-RES-02 — Empty state does not prove the timeline was never used

The document claims `GetStartFrame() == GetEndFrame()` plus empty tracks proves that no clip was ever inserted or deleted. It only describes the observed current state; a previously edited timeline may later have become empty. Replace the historical claim with current-state evidence and specify what establishes freshness (for example, app-owned pre-creation reservation plus operator attestation bound to the exact UIDs). If Resolve cannot supply stronger historical evidence, record that limitation and fail closed when the required attestation/reservation is absent.

### B5-D-R1-RES-03 — HMAC signer and trust root are undefined

`TrialExecutionAuthorization` includes an HMAC, while the procedure says the operator signs it using an application secret. An operator generally does not possess an app-held secret; an HMAC generated by the application proves integrity under that key, not by itself the identity or intent of the human. Define who may mint the authorization, how a fresh explicit human approval is captured, where the key is stored and scoped, the canonical bytes/fields signed, and how verification/rotation/revocation work. Do not describe the HMAC as a human signature unless the operator actually controls the signing key.
